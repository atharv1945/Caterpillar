# CAT Operator AI Companion - Frontend Architecture & Integration Guide

This document provides a comprehensive overview of the frontend codebase developed for the CAT Operator AI Companion. It details the architecture, describes the purpose of each file, highlights open points, and serves as a blueprint for integrating this frontend with a live backend system.

## 🏗️ Architecture Overview

The frontend is a single-page application built using:
- **Framework:** React 19 via Vite.
- **Styling:** Tailwind CSS (v4) with custom design tokens for the CAT brand (e.g., `cat-yellow`).
- **Animations:** Framer Motion for smooth transitions, dynamic overlays, and SVG micro-animations.
- **State Management:** Currently driven entirely by local React state in `LiveController.jsx`, which acts as the orchestrator for a simulated shift timeline.
- **Data Source:** A static mock database (`mockData.js`) that mirrors a planned relational database schema.

## 📂 File Directory Breakdown

### 1. Root & Configuration Files
- **`package.json` & `vite.config.js`:** Standard Vite + React configuration. Dependencies include `framer-motion` and Tailwind CSS.
- **`index.html`:** The HTML entry point. Includes Google Fonts (Poppins) and theme color settings for a mobile-first/tablet-first progressive web app feel.
- **`src/main.jsx` & `src/App.jsx`:** The React entry points. `App.jsx` simply mounts the `LiveController` which handles routing and state.
- **`src/index.css`:** Contains base Tailwind directives and any custom CSS variables (e.g., the `glass` utility class).

### 2. The Core Orchestrator (`src/demo/`)
This directory contains the simulation logic. In a production environment, this will be replaced or heavily modified to consume real API streams.

*   **`LiveController.jsx`**
    *   **Purpose:** The central nervous system of the app. It maintains an `elapsed` timer that acts as the "clock" for the shift, triggering events (idle, safety, weather) automatically as time passes. It handles view routing between Home, Task Detail, Training, and Overlays.
    *   **Open Points:** Needs to be decoupled from the local `elapsed` timer. State should be driven by a WebSocket connection or long-polling from the backend to receive live task states, alerts, and chat messages.
*   **`timeline.js`**
    *   **Purpose:** Defines the exact sequence of events for the demo (e.g., `IDLE_THRESHOLD_T`, `SAFETY_T`). It provides interpolation logic to animate progress bars and ETAs smoothly between keyframes.
    *   **Open Points:** This file simulates what the backend should provide. The ML ETA model (`ML_ETA_MODEL_OUTPUT`) and behavior insights are mocked here. In production, this file is mostly obsolete, replaced by real telemetry streams.
*   **`IntroSequence.jsx`**
    *   **Purpose:** Plays the initial splash screen animation before dropping into the live shift.

### 3. Screens (`src/screens/`)
These are the primary views the operator navigates between.

*   **`Home.jsx`**
    *   **Purpose:** The main dashboard showing the operator's current live task ("Now"), the next queued task, and later tasks.
    *   **Open Points:** Needs integration with a `GET /api/operator/schedule` endpoint.
*   **`TaskDetail.jsx`**
    *   **Purpose:** Deep dive into the active task. Shows a large progress ring, live ETA, load cycles, idle time, and AI reasoning ("Why this ETA?").
    *   **Open Points:** Data needs to update via a live telemetry stream. The "Why this ETA?" text should be generated by an LLM based on current site conditions.
*   **`CriticalAlert.jsx`**
    *   **Purpose:** A full-screen, high-priority red overlay triggered during safety events (e.g., seatbelt unfastened).
    *   **Open Points:** Needs to send an acknowledgment POST request to the backend (e.g., `POST /api/events/acknowledge`) when the operator taps "I've fastened my seatbelt".
*   **`IdleReasonPicker.jsx`**
    *   **Purpose:** Pops up when the AI detects prolonged idling, asking the operator for a reason.
    *   **Open Points:** Must POST the selected reason back to the backend to annotate the idle event.
*   **`TrainingHub.jsx` & `ShiftSummary.jsx` & `ResumeHandover.jsx`**
    *   **Purpose:** End-of-shift and training flows. Provides recommendations based on the day's performance.
    *   **Open Points:** Populate with real analytics and video content URLs from the backend.

### 4. Components (`src/components/`)
Reusable UI elements.

*   **`MascotBob.jsx`**
    *   **Purpose:** The visual representation of the AI Companion. Uses inline SVG and Framer Motion to animate between states: `normal`, `listening`, `warning`, `critical`, and `coaching`.
    *   **Open Points:** The state of Bob needs to be derived from the global application state (e.g., is the mic active? Is there an unread critical alert?).
*   **`ChatOverlay.jsx` & `ChatThread.jsx`**
    *   **Purpose:** The conversational UI. Allows the operator to text or voice-chat with Bob. Includes pre-scripted quick questions.
    *   **Open Points:** 
        *   **CRITICAL INTEGRATION:** Needs to connect to an LLM-backed chat endpoint (e.g., `POST /api/chat`).
        *   Voice integration requires implementing a Speech-To-Text (STT) browser API or streaming audio to the backend when the mic is active.
*   **`AnimatedNumber.jsx`, `ProgressBar.jsx`, `ProgressRing.jsx`, `StatTile.jsx`**
    *   **Purpose:** Data visualization components designed to look premium and animate smoothly as numbers change.
    *   **Open Points:** Ensure the props passed to these match the data types coming from the real GraphQL/REST API.
*   **`BottomRightBob.jsx` & `BobDock.jsx`**
    *   **Purpose:** The sticky trigger buttons to open the ChatOverlay.

### 5. Data & Utilities (`src/utils/` & `src/mockData.js`)

*   **`mockData.js`**
    *   **Purpose:** A crucial file for understanding the expected data contracts. It contains arrays for `operators`, `tasks`, `telemetry`, `idle_events`, and `safety_events` that closely mirror the planned SQL database schema.
    *   **Open Points:** Use this file as the exact blueprint for building your backend JSON serializers. Once the API is live, this file can be deleted.
*   **`utils/sound.js` & `utils/getValueOrFallback.js`**
    *   **Purpose:** Helpers for playing notification chimes and safely falling back to hardcoded numbers if simulated ML models fail.

## 🚀 Integration Action Plan

To transition this frontend from a simulated demo to a live application, follow these steps:

1.  **State Management Overhaul:** Introduce a global state manager (like Zustand or Redux) or React Context to replace the local state in `LiveController.jsx`. 
2.  **WebSocket Connection:** Establish a WebSocket connection upon app load to receive real-time updates for:
    *   Machine Telemetry (progress, ETA, cycles, engine hours)
    *   Safety Events (triggering `CriticalAlert`)
    *   System Events (triggering `IdleReasonPicker`)
3.  **API Client Implementation:** Create an API service layer to handle CRUD operations:
    *   Fetch schedule/tasks on load.
    *   Submit idle reasons.
    *   Acknowledge safety alerts.
    *   Send/receive chat messages.
4.  **Chat & Voice:** Swap the hardcoded `chat_quick_questions` logic in `ChatOverlay.jsx` with an async function that sends user queries to the backend LLM orchestrator and awaits the streaming response.
5.  **Remove Demo Logic:** Deprecate `timeline.js` and the `elapsed` interval inside `LiveController.jsx`. The UI should purely react to incoming backend data.
